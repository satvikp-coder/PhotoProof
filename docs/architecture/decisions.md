# Architectural decisions

Short records of decisions that shape the codebase. Add a new entry (never rewrite an
old one) when a decision changes.

### ADR-001 · Single process, sequential executor first
Four developers, local workloads. A sequential executor behind the `Executor`
protocol is enough and deterministic. Parallel and process-isolated executors are
backlog items and must implement the same protocol.

### ADR-002 · `app.toml` is the version source of truth
Hatchling's regex version source reads `app.toml`, so the package version cannot
drift. CI builds the wheel and compares its metadata to `app.toml`.

### ADR-003 · Universal, hash-pinned lockfiles generated by uv
`requirements.lock` is a single universal file (all OSes, Python 3.11–3.15) with
`--hash` for every artifact, installed with `pip --require-hashes --only-binary :all:`.
The build backend (hatchling) is locked too, so the editable install needs no network
and no build isolation.

### ADR-004 · Plugins are trusted code discovered from a code-defined package
Discovery only walks `photoproof.plugins` (tests pass a fixture package explicitly).
Configuration cannot add discovery locations. Importing a plugin is **not** a sandbox.

### ADR-005 · Metadata as a plain dict in `__init__.py`, implementation lazy
Invalid metadata is reported as an unavailable plugin instead of crashing discovery,
and `processor.py` is imported only when the plugin runs.

### ADR-006 · Graph errors fail loudly; policy effects block
Structural graph problems are developer errors (`PlanningError`). Policy effects that
make a profile unable to operate yield a `BLOCKED` result so the system never reports
an apparently complete analysis.

### ADR-007 · Persistence through critical event subscribers
Run and plugin state are written by a critical subscriber on the event bus. Optional
subscribers are isolated; critical failures raise `EventDeliveryError`.

### ADR-008 · Run-level cache keyed on everything
The cache key includes inputs, mode, profile, the full effective settings, flags,
policy decisions, plugin versions and implementation digests, plugin configs, relevant
distribution versions and the pipeline fingerprint. This over-invalidates (for example
on a log-level change) but cannot reuse a result computed under different conditions.
Per-plugin caching is a backlog item.

### ADR-010 · ruamel.yaml instead of PyYAML
PyYAML has no wheels for Python 3.15, and wheel-only installs are a launcher
requirement. ruamel.yaml's pure-Python safe loader works on every supported version and
rejects duplicate keys natively. Docs and security tools that still need PyYAML are
isolated in `requirements-tools.lock` (ADR-003).

### ADR-009 · No empty placeholder modules
Modules that would only contain `pass` are not created. Their absence is documented
here and in the backlog.

### ADR-011 · Durable job queue backed by SQLite

PhotoProof runs analyses synchronously in the caller's process. A web request
(WebKit, PP-039/PP-041) would block for the whole pipeline, and a crash loses the
request. We need a durable job queue so analyses can be submitted asynchronously
and survive restarts.

**Decision:** Use the existing SQLite database as the job queue, with a new `jobs`
table:

| Column | Type | Purpose |
|--------|------|---------|
| `job_id` | TEXT PK | Unique job identifier |
| `state` | TEXT | `queued` \| `running` \| `succeeded` \| `failed` \| `cancelled` |
| `payload` | TEXT | JSON-serialised `AnalysisRequest` (descriptors only) |
| `attempts` | INTEGER | Number of claim attempts |
| `max_attempts` | INTEGER | Max attempts before giving up (default 1) |
| `lease_until` | TEXT | ISO timestamp; job is free to re-claim after this |
| `worker_id` | TEXT | ID of the worker currently holding the lease |
| `idempotency_key` | TEXT UNIQUE | `sha256(request_json) + ":" + client_token` |
| `created_at` | TEXT | ISO timestamp of creation |
| `updated_at` | TEXT | ISO timestamp of last change |
| `error_message` | TEXT | Failure reason, if any |

Claims use `BEGIN IMMEDIATE` + `UPDATE ... RETURNING` so that two workers cannot
both claim the same job. Leases expire after `jobs.lease_seconds`; `requeue_stale()`
re-queues expired leases (up to `max_attempts`) or marks them failed.

WAL mode (`PRAGMA journal_mode=WAL`) is enabled on the database connection. This
allows concurrent readers (plugin pipeline reading job state) and a single writer
(job queue claiming/finishing jobs) without blocking each other. WAL mode is
persistent once set, so it survives restarts. Backup implications: the WAL file
(`-wal`) and shared-memory file (`-shm`) must be included in backups, or the
database must be checkpointed before backup (`PRAGMA wal_checkpoint(TRUNCATE)`).

**Consequences:**

- No new infrastructure (no Redis, Celery, or message broker).
- Jobs survive application restarts.
- Idempotent submission: same request + client token returns the same `job_id`.
- At-least-once execution: stale leases are re-queued or failed after
  `max_attempts`.
- SQLite is a single file; high write contention could become a bottleneck at
  very large scale (not expected for this project).
- WAL files must be managed in backup procedures.

**Related:** PP-050 (this issue), PP-051 (worker supervision), PP-039/PP-041 (WebKit).

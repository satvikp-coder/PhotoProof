# Architectural decisions

Short records of decisions that shape the codebase. Add a new entry (never rewrite an
old one) when a decision changes.

### ADR-001 · Single process, sequential executor first
Four developers, local workloads. A sequential executor behind the `Executor`
protocol is enough and deterministic. Parallel and process-isolated executors are
backlog items and must implement the same protocol.

### ADR-002 · `app.toml` is the version source of truth
Hatchling's regex version source reads `app.toml`, so the package version cannot
drift. CI builds the wheel and compares its metadata to `app.toml`.

### ADR-003 · Universal, hash-pinned lockfiles generated by uv
`requirements.lock` is a single universal file (all OSes, Python 3.11–3.15) with
`--hash` for every artifact, installed with `pip --require-hashes --only-binary :all:`.
The build backend (hatchling) is locked too, so the editable install needs no network
and no build isolation.

### ADR-004 · Plugins are trusted code discovered from a code-defined package
Discovery only walks `photoproof.plugins` (tests pass a fixture package explicitly).
Configuration cannot add discovery locations. Importing a plugin is **not** a sandbox.

### ADR-005 · Metadata as a plain dict in `__init__.py`, implementation lazy
Invalid metadata is reported as an unavailable plugin instead of crashing discovery,
and `processor.py` is imported only when the plugin runs.

### ADR-006 · Graph errors fail loudly; policy effects block
Structural graph problems are developer errors (`PlanningError`). Policy effects that
make a profile unable to operate yield a `BLOCKED` result so the system never reports
an apparently complete analysis.

### ADR-007 · Persistence through critical event subscribers
Run and plugin state are written by a critical subscriber on the event bus. Optional
subscribers are isolated; critical failures raise `EventDeliveryError`.

### ADR-008 · Run-level cache keyed on everything
The cache key includes inputs, mode, profile, the full effective settings, flags,
policy decisions, plugin versions and implementation digests, plugin configs, relevant
distribution versions and the pipeline fingerprint. This over-invalidates (for example
on a log-level change) but cannot reuse a result computed under different conditions.
Per-plugin caching is a backlog item.

### ADR-010 · ruamel.yaml instead of PyYAML
PyYAML has no wheels for Python 3.15, and wheel-only installs are a launcher
requirement. ruamel.yaml's pure-Python safe loader works on every supported version and
rejects duplicate keys natively. Docs and security tools that still need PyYAML are
isolated in `requirements-tools.lock` (ADR-003).

### ADR-009 · No empty placeholder modules
Modules that would only contain `pass` are not created. Their absence is documented
here and in the backlog.

### ADR-011 · Server-rendered WebKit foundation

**Decision (issue #38):** use FastAPI + Jinja2, with HTMX as a future progressive
enhancement. This is implemented for review; merge/review occurs through the issue PR.
The current read-only shell needs no JavaScript, so HTMX is not downloaded or bundled.

| Criterion | FastAPI + Jinja2 + optional HTMX | Streamlit | NiceGUI |
|---|---|---|---|
| Accessibility | Direct control of semantic HTML, focus, contrast and no-JS navigation; we must test it | Convenient widgets; less direct markup/layout control | Python components over a client UI framework; component accessibility still requires browser testing |
| Security | Explicit middleware, autoescaped SSR, same-origin CSRF and a small CSP surface | Framework-managed server/client interaction; custom CSP and request boundaries are less direct | FastAPI underneath, plus a stateful client/component layer to secure |
| Testing | ASGI TestClient plus browser/axe tests for actual markup | AppTest is useful for Streamlit behavior; browser checks still needed | Component/browser testing with an additional client lifecycle |
| Dependencies | Small ASGI/template stack; no native server extras or JS in the shell | Larger data-app stack | Adds UI components, client runtime and live connection machinery |
| Routing/SSR | Explicit routes and reusable server templates; normal links work without JS | App/page model and rerun lifecycle | Python page functions plus client component state |
| Future uploads | Own the streaming request, size limits and ingestion boundary | File-uploader widget is convenient but less suited to a custom streaming boundary | Upload components available; custom limits still need server integration |

The comparison is our architecture assessment based on the projects' primary docs:
[FastAPI templates](https://fastapi.tiangolo.com/advanced/templates/),
[Starlette TestClient](https://starlette.dev/testclient/),
[HTMX](https://htmx.org/docs/),
[Streamlit architecture](https://docs.streamlit.io/develop/concepts/architecture/architecture),
and [NiceGUI](https://github.com/zauberzeug/nicegui).
FastAPI/Jinja gives this team control over evidence handling and markup without
introducing an SPA. Tradeoffs: we own CSS, CSRF, accessibility and lifecycle testing;
there is more initial work than Streamlit and no ready-made image-workbench widgets.

WebKit owns presentation only: `bootstrap()` supplies identity/settings/registries,
`default_registry(deep=False)` supplies quick health checks and `decide_all()` supplies
plugin eligibility with `OverrideOrigin.WEB`. An additive origin argument closes the
boundary even if a CLI override token is accidentally supplied. No request can repair
state or start analysis. Core SQLite connections remain on the owning ASGI thread;
async routes do not dispatch database work into a thread pool. Long jobs will require
the later jobs design; they must not be run in the request event loop.

Runtime additions are FastAPI (MIT), Jinja2 and Uvicorn (BSD-3-Clause). Dev-only httpx2
(BSD-3-Clause) supports current Starlette's TestClient; plain httpx is deprecated by
Starlette. All three Python lockfiles are regenerated by uv, not hand-edited. WebKit
and its templates/static assets are included in wheel and sdist. `main.py` stays
standard-library-only and delegates the `web` command through the existing CLI.

Review follow-up: the CLI owns startup/shutdown and injects services into the factory.
Diagnostics caches a redacted snapshot for 30 seconds and uses worker-owned read-only
database services. Loopback-only binding applies to every environment until
authentication exists, as explicitly agreed during review. HEAD/Allow semantics and
local application error logging are part of the HTTP foundation.
